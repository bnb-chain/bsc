Construire sur Coinbosa Chain

La chaîne est compatible EVM : MetaMask, Hardhat, Foundry, ethers.js et viem s'y connectent sans adaptation. Cette page décrit ce qui fonctionne, et dit où sont les bornes — celles du point d'accès public comme celles du réseau.

Démarrage

Trois champs, et le réseau est joignable.

Un réseau EVM se décrit par une poignée de valeurs. Elles ne sont pas des intentions : elles s'appliquent à chaque bloc et se relisent sur la chaîne.

ChampValeur à saisir
Nom du réseauCoinbosa Chain
Nouvelle URL de RPChttps://explorer.coinbosa.com/rpc
Identifiant de chaîne26262 — 0x6696 en hexadécimal
Symbole de la monnaieBOSA
Décimales18
URL de l'explorateurhttps://explorer.coinbosa.com

1 — Ouvrir l'ajout manuel

Dérouler le sélecteur de réseau, puis « Ajouter un réseau » et « Ajouter un réseau manuellement ». Cette saisie est obligatoire : le chainId 26262 n'étant enregistré dans aucun annuaire public, Coinbosa n'apparaît dans aucune liste préremplie.

2 — Recopier les champs

Le portefeuille interroge le point d'accès et refuse l'enregistrement si l'identifiant renvoyé par le nœud ne correspond pas à celui saisi. Ce contrôle protège contre un point d'accès qui se ferait passer pour un autre réseau.

3 — Vérifier avant de signer

Les soldes s'affichent en BOSA et le dernier bloc avance toutes les cinq secondes environ. S'il n'avance plus, la cause est du côté du nœud : un seul validateur produit les blocs, et rien ne prend le relais.

Les 18 décimales ne sont pas un réglage. L'unité de base d'une machine virtuelle Ethereum est le wei, valeur câblée dans le calcul du gas comme dans tous les portefeuilles. Aucun champ ne permet de la changer.

Connexion

Ajouter le réseau par le code.

Une application peut proposer l'ajout du réseau en une invite, sans que l'utilisateur recopie quoi que ce soit.

wallet_addEthereumChain 
await window.ethereum.request({
  method: 'wallet_addEthereumChain',
  params: [{
    chainId: '0x6696',
    chainName: 'Coinbosa Chain',
    nativeCurrency: { name: 'Coinbosa', symbol: 'BOSA', decimals: 18 },
    rpcUrls: ['https://explorer.coinbosa.com/rpc'],
    blockExplorerUrls: ['https://explorer.coinbosa.com']
  }]
});

L'identifiant se transmet en hexadécimal

26262 s'écrit ici 0x6696, préfixé et sans zéro de tête. C'est l'erreur la plus fréquente de cette étape : un identifiant passé en décimal est rejeté, souvent sans message explicite. eth_chainId renvoie la même forme.

L'invite n'est pas une garantie

N'importe quel site peut demander l'ajout d'un réseau, sous le nom et le symbole de son choix. Ce qui identifie une chaîne, c'est son identifiant, l'empreinte de son bloc 0 et l'adresse du point d'accès.

Outillage

Configurer Hardhat et Foundry.

Aucun greffon spécifique n'est nécessaire : pour ces outils, Coinbosa Chain est un réseau EVM comme un autre. Seule la version d'EVM visée demande une attention.

hardhat.config.js 
module.exports = {
  solidity: {
    version: '0.8.26',
    settings: { evmVersion: 'shanghai' }
  },
  networks: {
    coinbosa: {
      url: 'https://explorer.coinbosa.com/rpc',
      chainId: 26262,
      accounts: [process.env.CLE_PRIVEE]   // jamais en clair dans le dépôt
    }
  }
};
foundry.toml 
[profile.default]
solc_version = "0.8.26"
evm_version = "shanghai"

[rpc_endpoints]
coinbosa = "https://explorer.coinbosa.com/rpc"

# forge script script/Deploy.s.sol \
#   --rpc-url coinbosa --broadcast

Compilez pour Shanghai, pas pour Cancun. Les forks postérieurs à Kepler ne sont pas activés. Or Solidity vise Cancun par défaut : sans evmVersion: 'shanghai', le compilateur produit l'opcode MCOPY, que la chaîne rejette — la compilation réussit, le déploiement échoue.

Jetons

Le standard BRC20.

BRC20 — Bosa smart contract 20 — est le standard de jeton de la chaîne. Son interface est compatible ERC-20 : tout portefeuille, toute passerelle, tout service qui parle ERC-20 fonctionne sans adaptation.

IBRC20.sol — interface minimale 
interface IBRC20 {
    function name()        external view returns (string memory);
    function symbol()      external view returns (string memory);
    function decimals()    external view returns (uint8);
    function totalSupply() external view returns (uint256);
    function getOwner()    external view returns (address);

    function balanceOf(address compte) external view returns (uint256);
    function allowance(address proprietaire, address delegue) external view returns (uint256);

    function transfer(address vers, uint256 montant) external returns (bool);
    function approve(address delegue, uint256 montant) external returns (bool);
    function transferFrom(address de, address vers, uint256 montant) external returns (bool);

    event Transfer(address indexed de, address indexed vers, uint256 montant);
    event Approval(address indexed proprietaire, address indexed delegue, uint256 montant);
}

La propriété se transmet en deux temps

C'est le seul écart de comportement notable avec un ERC-20 courant. transferOwnership désigne un destinataire en attente, sans rien céder ; la propriété ne change que lorsque celui-ci appelle acceptOwnership depuis son adresse.

Pourquoi ce détour

Un transfert en une seule étape vers une adresse mal saisie est irréversible : personne n'en détient la clé, aucune fonction réservée au propriétaire ne peut plus être appelée, le contrat reste orphelin pour toujours. La seconde étape prouve que le destinataire contrôle l'adresse.

Ce que BRC20 ajoute

getOwner expose le propriétaire de façon standardisée. mint est réservé au propriétaire et se clôt définitivement par finishMinting ; burn est ouvert au porteur. Enfin, increaseAllowance et decreaseAllowance évitent la condition de course de approve.

Un standard homonyme existe sur Bitcoin, sans rapport technique. Le BRC-20 des inscriptions Ordinals ne partage avec celui-ci que le nom : écrire « BRC20 de Coinbosa » lève l'ambiguïté.

Surface exposée

Ce que le RPC public accepte, et ce qu'il refuse.

Le nœud public sert à lire la chaîne et à y déposer des transactions signées. Ce qui permettrait de l'inspecter ou de le piloter est fermé, et les requêtes coûteuses sont bornées : sans borne, une demande de deux cents octets peut exiger le balayage de toute la chaîne.

Deux limites à connaître avant de bâtir dessus. Il n'existe pas de point d'accès WebSocket : les abonnements sont indisponibles, une application doit sonder le nœud. Et l'historique d'état n'est pas garanti sur toute la profondeur de la chaîne — lire un solde à un bloc ancien demanderait un nœud d'archive, qui n'est pas déployé.

Contrats système

Ce qui est déployé au bloc 0, et pourquoi c'est figé.

Un réseau dérivé de BNB Smart Chain hérite de contrats pré-déployés à des adresses réservées. L'un d'eux gouverne le consensus, et sa présence au bloc 0 engage l'identité du réseau.

Le contrat du consensus

À l'adresse 0x…1000, il fournit au moteur la liste des validateurs à chaque bloc d'epoch, tous les 200 blocs. Le bytecode hérité, daté de 2021, n'expose pas la fonction appelée alors : l'appel échoue, la chaîne s'arrête au bloc 200.

Un remplacement écrit pour l'occasion

CoinbosaValidatorSet expose exactement la surface d'appel attendue, et rien de plus : 5 758 octets contre 16 429. Le correctif du réseau amont ne vaut que pour ses propres réseaux, reconnus à l'empreinte de leur genesis.

Aucune fonction ne peut échouer

C'est la règle de conception : sur le chemin du consensus, un échec rend le bloc improduisible et arrête le réseau. Le franchissement d'un bloc d'epoch est donc rejoué à chaque évolution du code.

Empreinte du bloc 00x8dcdadc247a98f33728cae944e20ce7c49c74b35cfba31495f85e98979018da6
Racine d'état du bloc 00x93682eb9182a55531d47014b76a285b45d3e720a2951f9ffbdc67f52995f8c03
Premier bloc scellé7 août 2026

Ce bytecode est figé, et c'est une propriété, pas une limite subie. Il appartient à l'allocation du bloc 0 : son contenu entre dans le calcul de l'empreinte ci-dessus, donc dans l'identité de la chaîne. En modifier la logique produirait un autre bloc 0 — un autre réseau, inatteignable depuis celui en production.

Vérification

Le code est ouvert, et le genesis se rejoue.

Un projet qui demande la confiance doit donner les moyens de vérifier sans lui. Le client, les contrats, le genesis et les scripts sont publiés, et la reconstruction du réseau est rejouée.

Ce que contient le dépôt

Le client, dérivé de bnb-chain/bsc, les quatre contrats — interface, implémentation de référence, jeton de démonstration et contrat système —, le genesis, les scripts et la documentation, sur le dépôt.

Un seul écart de consensus

Le point d'ancrage amont est épinglé par empreinte de commit, pas par une étiquette qu'on peut redéplacer. Sur le code du client, l'écart tient en une ligne : l'intervalle de bloc porté de 3 000 à 5 000 millisecondes. D'où l'obligation de compiler ce dépôt — le binaire officiel du réseau amont produit des blocs de 3 secondes.

Rejoué à chaque envoi de code

Sur une machine vierge, l'intégration continue recompile le client, régénère le genesis, démarre un nœud, puis contrôle le temps de bloc, l'offre, l'empreinte du bloc 0, le banc BRC20 et le franchissement d'un bloc d'epoch.
